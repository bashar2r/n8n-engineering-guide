01

The Core Misconception

Why you usually don't need Loop Over Items

Every lesson since Day 1 has relied on one fact: every n8n node automatically processes the full items array it receives, one item at a time, without you writing any loop. A Set node with 500 incoming items transforms all 500. A Postgres Insert node with 1,000 incoming items inserts all 1,000. This is n8n's default behavior — implicit looping — and it's true regardless of whether Loop Over Items is anywhere in your workflow.

The Single Most Common Beginner Mistake

Reaching for Loop Over Items purely out of a traditional-programming reflex ("I need to process a list, so I need a for-loop"), when the workflow would have worked identically without it. This is confirmed directly in n8n's own documentation.

❌ Wrong

Adding Loop Over Items to "process every item" when a single Set node would handle all 500 items natively.

✅ Correct

Use implicit per-item processing by default. Reach for Loop Over Items only for its three real use cases.

02

The Three Genuine Reasons

When Loop Over Items is actually required

1

Node Exceptions

A small number of nodes are documented to only process the first item they receive, ignoring the rest of the array entirely. The RSS Feed Read node is n8n's own cited example. If you need that kind of node to run once per item, you must feed it one item at a time via Loop Over Items.

2

Rate-Limit Control

Batching 500 API calls into groups of 10, with a pause between each group, keeps you under a documented rate limit. This connects directly back to Day 4's 429 handling.

⚠️ CRITICAL GOTCHA

The loop alone does nothing to protect you — without a Wait node placed between the API call and the loop-back connection, the batches fire as fast as the engine can process them, and you'll hit the same rate limit you were trying to avoid. The loop controls grouping; the Wait node controls pacing. You need both.

3

Dynamic / Manual Pagination

The mechanism referenced back in Day 4 as an alternative to the built-in Pagination toggle. Today closes that gap. See Section 03 for the full Reset mechanism explanation.

03

The Reset Mechanism

How manual pagination actually works

By default, Loop Over Items keeps working through its original input list, batch by batch, until that list is exhausted — it doesn't care what flows back into it afterward. Reset mode changes this fundamentally: when Reset is turned on, every time data loops back into the node, the node treats that new incoming data as a completely fresh list to iterate — not a continuation of the original one.

Manual Pagination Loop Architecture n8n workflow logic 
// Conceptual flow of a Reset-mode pagination loop:

[Loop Over Items: Reset ON]
        │
        ▼
[HTTP Request: fetch current page]
        │
        ▼
[IF: does response indicate more pages exist?]
        │true                              │false
        ▼                                   ▼
[Set: build "next page" request data]   [continue to rest
        │                                 of workflow]
        └──── loops back to ─────────────────┐
                                              │
              [Loop Over Items: Reset ON] ◄───┘
              (treats the "next page" data as
               its new current-iteration input —
               NOT the original first-page data)

Day 4 — Built-in Pagination

Handles fetch→check→repeat cycle internally within a single HTTP Request node, using response and pageCount automatically. Clean, compact, but limited to offset/cursor/Link header strategies.

Day 8 — Manual Loop + Reset

The hand-built version of the same idea — more verbose, but necessary when an API's pagination shape doesn't fit any of Day 4's three built-in strategies. You control every step.

Mandatory Safety Rule

Every loop like this must have a valid termination condition. If the "does more data exist" check can never evaluate false, the execution runs forever, consuming a worker indefinitely — this is the same resource-exhaustion risk from Day 4's timeout discussion, self-inflicted this time rather than caused by an unresponsive external API.

04

Production Debugging Pitfall

IF node inside a loop causing inflated item count

A specific, documented gotcha: if you place an IF node inside a loop, and both the true and false branches reconnect back into the loop separately, your item count can inflate beyond the actual number of records — each branch contributes its own count back to the loop rather than the two branches being treated as one unified continuation.

🔴 Symptom

Loop Over Items execution processing what looks like more items than you started with. The execution count keeps growing mysteriously.

🟢 Fix

Check the branching-reconnection pattern first. Ensure both IF branches don't independently feed back into the loop. Merge them before reconnecting, or use a single continuation path.

05

The Merge Node — Modes

Nothing recombines automatically in n8n

The Merge node takes two (or more) separate branches and combines them into one stream. If a workflow splits into parallel branches, they stay separate all the way to the end unless you explicitly merge them. (Useful to know: n8n also lets you find this node by searching "Join" — the same node, a more SQL-familiar alias.)

A

APPEND

Input 1: [A, B, C]
Input 2: [D, E, F]
Output:  [A, B, C, D, E, F]

No matching, no pairing — just concatenation. Use when two independent sets should be processed together downstream (e.g., active users + inactive users).

P

COMBINE › Position

Input 1: [A, B, C]
Input 2: [X, Y, Z]
Output:  [A+X, B+Y, C+Z]

Paired by index/order only. Use only when both inputs are guaranteed to be in the same order and the same length — fragile if not.

M

COMBINE › Matching Fields

Input 1: [{id:1,...}, {id:2,...}]
Input 2: [{id:1,...}, {id:2,...}]
Match: id ↔ id
// SQL-join equivalent — pairs by shared key

Pairs records by a shared key regardless of order or list length. This is the SQL-join equivalent.

S

SQL QUERY

v1.49.0+

Write an actual SQL-style query across the input streams for complex joins beyond the simpler modes above.

SELECT * FROM input1
LEFT JOIN input2 ON input1.id = input2.id
C

CHOOSE BRANCH

Passes through exactly one of the inputs — useful when you need to conditionally select one data source over another rather than truly combining them.

06

Combine › Matching Fields

The Four Output Types — your SQL-join mental model

KEEP MATCHES

INNER JOIN

Only records present in BOTH inputs survive. Unmatched records from either side are dropped entirely.

KEEP NON-MATCHES

ANTI-JOIN

Only records that DON'T have a match survive. Useful for "find customers with no billing record."

KEEP EVERYTHING

FULL OUTER JOIN

Matched records are merged together; unmatched records from BOTH sides are also kept, just without the other side's fields filled in.

ENRICH INPUT 1

LEFT JOIN

Every record from Input 1 survives, matched or not. Where a match exists in Input 2, its fields are added. Where no match exists, Input 1's record passes through unchanged. This is the correct choice whenever Input 1 is your "source of truth" list that must never shrink.

Operational Details

01

If you need to match on a nested field, the Input 1 Field / Input 2 Field boxes require dot-notation typed as literal text — not wrapped in {{ }} expression syntax.

02

Architecturally important: The Merge node always waits for every connected input to have data before it executes at all. If one branch feeding it is a slow API call and the other is a fast Set node, the fast branch's output sits idle until the slow branch finishes — the Merge node, and everything after it, only ever runs as fast as the slowest parallel path feeding it.

07

Rate-Limit Loop Gotcha

Loop without Wait = still hits 429

SILENTLY BROKEN 

// Loop Over Items (batch: 10)
    │
    ▼
[HTTP Request: API Call]
    │
    └──── loops back ─────┐
                          │
              [Loop Over Items] ◄───┘

// NO Wait node = batches fire at full speed
// Result: 429 Rate Limit errors still occur
  • ❌ Loop controls grouping only
  • ❌ No pacing between batches
  • ❌ API still overwhelmed

CORRECT 

// Loop Over Items (batch: 10)
    │
    ▼
[HTTP Request: API Call]
    │
    ▼
[Wait: 60 seconds]
    │
    └──── loops back ─────┐
                          │
              [Loop Over Items] ◄───┘

// Wait node enforces 60s pause between batches
// Result: stays under 10 req/min limit
  • ✅ Loop controls grouping
  • ✅ Wait controls pacing
  • ✅ Rate limit respected

B Keep Non-Matches (ANTI-JOIN) — only customers with NO billing record survive
