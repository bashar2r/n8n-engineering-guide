The Two-Node Architecture

Parent workflow calls child workflow — the exact data contract

Sub-workflows are built from two complementary nodes: Execute Sub-workflow (in the parent) and Execute Sub-workflow Trigger (in the child). The parent calls the child; the child runs its logic; the child's last node output returns to the parent. Nothing more, nothing less.

Parent ↔ Child Data Contract n8n architecture 
PARENT WORKFLOW                          CHILD (SUB-)WORKFLOW

[[some node]]                            [Execute Sub-workflow Trigger]
      │                                   (label: "When executed by another workflow")
      ▼
[Execute Sub-workflow] ───calls───►        receives parent's input data
      │                                              │
      │                                              ▼
      │                                   [... sub-workflow logic runs ...]
      │                                              │
      │                                              ▼
      │                                   [Last node of sub-workflow]
      │                                              │
      ◄──── this node's output IS what ──────────────┘
             the last node produced —
             the "return statement"

The Exact Contract

The Execute Sub-workflow node passes its input data to the child's Execute Sub-workflow Trigger. Whatever the child's last node outputs is exactly what returns to the parent. If you want the parent to receive specific fields, make sure the last node in the child produces exactly that shape — a Set node with "Keep Only Specified Fields" is the natural choice.

02

Designing the Input Contract

Three modes — one professional default

1

ACCEPT ALL DATA

Whatever the parent sends passes through unchanged — no schema, no validation. Fast to set up, but the sub-workflow gives no signal about what it actually expects.

// No contract — parent sends anything, child receives everything
// Risk: silent failures when expected fields are missing
2

DEFINE USING FIELDS BELOW

PROFESSIONAL DEFAULT

You name each expected input field explicitly, with a type (string / number / boolean / JSON) and mark it required or optional. This is a genuine contract — anyone opening this sub-workflow six months from now can read exactly what it needs without reverse-engineering the logic.

// Explicit, self-documenting contract
channel: string (required)
message: string (required)
priority: string (optional)
metadata: JSON (optional)
3

DEFINE USING JSON EXAMPLE

You provide one sample JSON object showing the expected shape, and n8n infers the contract from it — faster to write than listing fields individually, at some cost to the explicit self-documentation of the fields approach.

{
  "channel": "slack",
  "message": "Server alert",
  "priority": "high"
}

⚠️ The Difference

"Define using fields below" is the difference between a function with a clear signature and one that just accepts *args, **kwargs and hopes for the best. For anything you intend to reuse across multiple client workflows — which is the entire point of sub-workflows — this is the professional default.

03

Three Legitimate Reasons

When and why to build a sub-workflow

1

Genuine Reusability

The same logic, called from multiple unrelated parent workflows. The "Send Formatted Alert" sub-workflow is the clearest case — one alerting standard across every client's Error Workflow.

// One sub-workflow: "Send Formatted Alert"
// Called from: Client A Error Workflow
// Called from: Client B Error Workflow
// Called from: Client C Scheduled Report
// Fix formatting once → fixed everywhere
2

Retry-Isolation

You already used this in Day 6 and Day 7 without naming it. Isolate a flaky external call in its own workflow with On Error: Stop Workflow so Retry On Fail actually engages. The parent is set to Continue (using error output) — giving one small piece of logic a different failure-handling scope than the rest of the pipeline.

Child (Isolated)
On Error: Stop Workflow
Retry On Fail: 3 attempts
// Flaky API call isolated here
Parent (Resilient)
On Error: Continue (Error Output)
// Parent never stops —
// handles child failure gracefully
3

Memory & Scale

Confirmed directly in n8n's own docs: for a workflow that's grown large enough to process genuinely large datasets in one canvas, splitting logical sections into sub-workflows is documented to help with memory pressure specifically — this isn't only an organizational nicety, it's an actual performance consideration for heavy workloads.

04

Convert to Sub-workflow

The Merge node constraint — callback to Day 8

n8n has a convenient shortcut: select a contiguous run of nodes, right-click → Convert to sub-workflow, and n8n automatically extracts them into a new workflow, builds the trigger with inferred input parameters, and replaces the section with an Execute Sub-workflow node.

CANNOT CONVERT

A selection that starts at a Merge node cannot be converted to a sub-workflow.

// Branch A ──┐
//             ├──► [Merge] ──► [Node X] ──► [Node Y]
// Branch B ──┘
//                    ^
//                    └─ can't start extraction here
// Merge has 2+ incoming connections
// Sub-workflow needs exactly 1 entry point

SOLUTION

Either include both branches feeding the Merge inside the selection, or restructure so the extraction point sits after the Merge has already resolved to one stream.

// Branch A ──┐
//             ├──► [Merge] ──► [Node X] ──► [Node Y]
// Branch B ──┘                    ^
//                                   └─ extract from here
// Single stream after Merge = valid entry point

This makes complete sense once you know why: a Merge node's entire job (from Day 8) is combining two or more separate incoming branches — by definition it has more than one incoming connection. A sub-workflow's input, by contrast, is a single, well-defined data contract.

05

Credentials

Reference locally — never pass as data

The Golden Rule

Following the same principle from Day 4 (credentials are encrypted references, never exposed in workflow JSON): if a sub-workflow needs to call an authenticated API, that credential should be configured directly inside the sub-workflow's own HTTP/database node — not decrypted and handed to it as a data field from the parent.

❌ WRONG — Pass as Data

  • • Secret appears in execution logs
  • • Visible in data passed between nodes
  • • Potentially leaked in error payloads to Error Workflow
  • • Defeats the entire credential encryption system

✅ CORRECT — Reference Locally

  • • Credential lives only inside sub-workflow
  • • Parent never sees or handles the secret
  • • Encrypted reference, never exposed in data
  • • Same security model as Day 4's HTTP Request node

How sub-workflow executions are counted

Knowledge Check

3 questions — test your understanding

Q1. A parent workflow calls a sub-workflow. What specific piece of the child's execution returns to the parent?

A Everything the sub-workflow produced across all its nodes, merged together
B Only the output of the sub-workflow's last node — its "return statement"
C The input data that was originally passed from the parent, unchanged

Q2. You're building a "Send Alert" sub-workflow to reuse across 5 client projects. Which input contract mode is the professional default?

A Accept All Data — fastest to set up, no schema needed
B Define Using JSON Example — one sample object, n8n infers the rest
C Define Using Fields Below — explicit typed contract with required/optional flags

Q3. Why can't a node selection starting at a Merge node be converted to a sub-workflow?

A Merge nodes are too complex — n8n simply doesn't support converting them
B A Merge node has multiple incoming connections by definition, but a sub-workflow needs exactly one entry point
C Merge nodes require credentials, and sub-workflows can't access parent credentials
