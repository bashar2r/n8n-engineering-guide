01

The Binary Data Model

A genuinely separate layer from $json

Every item you've worked with since Day 1 has this shape. The critical distinction: json.fileName is just a text field — it tells you nothing about whether actual file content exists. The real file content lives entirely under binary, base64-encoded, under a named property.

Item Structure — Binary vs JSON n8n data model 
{
  "json": {
    "fileName": "report.pdf",
    "size": 102400
  },
  "binary": {
    "data": {
      "mimeType": "application/pdf",
      "fileName": "report.pdf",
      "fileExtension": "pdf",
      "data": "JVBERi0xLjQK..."
    }
  }
}

Why {{ $json.fileContent }} Can Never Work

Expressions like {{ $json.someField }} can never see into binary at all — it's a structurally separate part of the item, not a nested JSON field. The binary property is renameable, and you may see multiple binary properties on one item (e.g., data and data2) when a node outputs more than one file.

02

The Flagship Gotcha

Binary data can silently vanish

Certain Set (Edit Fields) node configurations discard an item's binary data entirely, with no warning, no error — the file is simply gone from that point forward. If you place a Set node between a file-download step and an Extract From File step, and its configuration doesn't preserve binary data, the very next node will fail with n8n's single most common file-related error: "No binary data found."

The Three Root Causes

1

A Node Upstream Stripped the Binary Data

A Set/Edit Fields node configured to keep only JSON, not binary. Check every node between the file's origin and where you're trying to use it.

2

The Binary Property NAME Doesn't Match

Node A outputs the file under "data". Node B's "Input Binary Field" looks for "data0". Must match EXACTLY, including case — copy it directly from the Binary tab in the previous node's output.

3

The Binary Data's TTL Has Expired

Production-specific — binary data can have a configured time-to-live. If a long-running or delayed workflow tries to access binary data after that window, it's gone.

⚠️ Safe Habit

Any time a file needs to survive a Set node, verify explicitly (in that node's output panel) that the Binary tab still shows your file after execution — don't assume it does just because the JSON side looks fine.

03

Getting Binary Data In

HTTP Request and beyond

HTTP Request — Response Format: File

Day 4 covered the HTTP Request node in depth but never mentioned this: to download an actual file rather than parse a JSON response, you must set the node's Response Format to File. The MIME type is detected automatically from response headers.

HTTP Request Node
  URL: https://api.example.com/download/report.pdf
  Response Format: File        ← CRITICAL SETTING
  ↓
Output item contains binary.data with:
  - mimeType: "application/pdf"
  - fileName: "report.pdf"
  - data: "JVBERi0xLjQK..."

Google Drive

Operation: Download — usable mid-workflow, not only as a trigger. Fetch a file based on data computed earlier in the same pipeline.

Google Drive
  Operation: Download
  File: {{ $json.driveFileId }}

Webhook (multipart/form-data)

When the caller sends multipart/form-data with a file attached, the webhook receives it as binary data directly.

Webhook Trigger
  HTTP Method: POST
  Content-Type: multipart/form-data
  → binary.data contains uploaded file

Self-Hosted Only

Read/Write Files from Disk and FTP/SFTP nodes do not work on n8n Cloud at all — a genuinely important fact to know before promising a client a local-filesystem-dependent architecture without first confirming their hosting model.

The Two Core Conversion Nodes

Moving between binary and JSON worlds

→

EXTRACT FROM FILE (binary → JSON)

Operations: Extract From CSV, XLS/XLSX, ODS, PDF (plain text), JSON, and "Binary To Property" mode that base64-encodes into a JSON string field without parsing structure.

CSV
Binary CSV
  → Extract From File
  → JSON rows
Excel
Binary XLSX
  → Extract From File
  → JSON rows + columns
PDF
Binary PDF
  → Extract From File
  → JSON with text
←

CONVERT TO FILE (JSON → binary)

Takes your items array and produces a binary file — CSV, XLSX, ODS, ICS, and others. Defaults to binary property "data" (renameable — every downstream node must use the new name).

JSON items array
  → Convert To File (CSV)
  → binary.data (downloadable CSV)

⚠️ XML Special Case

XML files need a two-step process — the XML node works on text, not binary:

Binary XML
  → Extract From File (as Text)
  → XML node
  → JSON

Trying to feed binary XML straight into the XML node doesn't work.

05

Storage Architecture

Where binary data actually lives

n8n has four binary storage modes, confirmed directly in current docs. Unlike most settings, the wrong choice here doesn't just produce bad data — it's the single most common cause of an n8n instance running out of memory in production.

MEMORY

DEFAULT

Fine for small files, low volume. Works fine until it doesn't — the most common cause of an n8n instance running out of memory under real file-processing load.

FILESYSTEM

⚠️ QUEUE BLOCKER

Writes to disk at a configured path. Solves memory problem for a single instance. NOT supported in queue mode — worker processes on different machines can't share one local filesystem. Hard architectural blocker.

S3

ENTERPRISE

AWS S3 or compatible. Works with queue mode — every worker can reach the same S3 bucket regardless of which machine it's running on. The correct choice for distributed deployments.

DATABASE

QUEUE OK

Stored alongside execution data. Also supports queue mode, but grows your database size and can hurt performance with large files.

The Rule That Matters Most

If a client's architecture needs queue mode (multiple worker processes) and needs binary data to persist reliably, filesystem mode is off the table by design — S3 (or database mode, with its own trade-off) is the only route. This is exactly the "verify the mechanism actually supports what the general architecture needs" discipline from Days 4–6, now applied to infrastructure.

06

Defensive Coding

Applying Day 3 discipline to binary data

The exact discipline from Week 1's Code node lesson, applied to files:

Binary Validation — Code Node defensive pattern 
const binary = $input.first().binary?.data;

if (!binary) throw new Error('No binary data found on this item');
if (!binary.fileName) throw new Error('Binary data is missing a fileName');
if (!binary.mimeType) throw new Error('Binary data is missing a mimeType');
if ((binary.data?.length || 0) < 100) throw new Error('File appears empty or corrupted');

return $input.all();

Security Note — Don't Trust the Label

A file's stated extension and MIME type are just metadata someone chose — they can be faked. A file named invoice.pdf is not guaranteed to actually be a PDF. For any workflow accepting untrusted uploads, treat the claimed type as a hint, not a guarantee, and validate structurally where it matters.

07

Knowledge Check

3 questions — test your understanding

Q1. You need to download a PDF file via HTTP Request. What setting must you configure?

A Set the HTTP Method to DOWNLOAD instead of GET
B Set Response Format to File — the MIME type is auto-detected from headers
C Add a Convert to File node after the HTTP Request to transform the JSON response

Q2. Your workflow processes thousands of large image uploads and the instance keeps running out of memory. What's the actual fix?

A Add more RAM to the server — memory is the only viable storage mode
B Switch binary storage from memory (default) to filesystem, S3, or database mode
C Use Loop Over Items to process images one at a time — this reduces memory usage

Q3. A client needs queue mode (multiple workers) AND must persist binary data reliably. Which storage mode is off the table?

A Filesystem mode — workers on different machines can't share one local filesystem
B Database mode — it stores files in the DB which hurts performance
C S3 mode — it's an enterprise-tier feature not available on all plans
