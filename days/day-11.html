— SECTION 01 — CRITICAL

A Webhook URL Is Not a Secret

An unauthenticated production webhook — n8n's default — accepts a request from anyone who has the URL, with no verification of who's actually sending it.

Default = Dangerous

The consequence isn't hypothetical: unauthorized POST floods cause the exact resource-exhaustion scenario from Day 6, and unvalidated payloads can inject fabricated data straight into whatever your workflow does next — a database write, a payment trigger, a notification to a real human.

Day 7 Gap

The Day 7 capstone's Order Intake webhook — the one accepting real order data — has zero authentication on it as built. Anyone who discovers that URL can submit fake orders indistinguishable from real ones.

— SECTION 02 — ARCHITECTURE

The Webhook Node's Four Built-In Options

Choosing the wrong one silently changes your workflow's security posture.

NONE Default

No verification of the caller at all. Accepts any request from anyone who has the URL. Only appropriate during prototyping.

BASIC AUTH Weakest Real Option

Username + password in the Authorization header. Works everywhere, but is the weakest real option — only appropriate when the caller genuinely supports nothing else.

HEADER AUTH Service-to-Service

A static token in a custom header you define (e.g., X-API-Key: <secret>). The standard choice for service-to-service integrations where you control both ends and can rotate the key yourself.

JWT AUTH Multi-Tenant

Validates a cryptographically signed JSON Web Token, supporting HMAC or RSA/ECDSA. Best suited to multi-tenant setups or callers that already issue JWTs.

The Confirmed JWT Gap

JWT Auth validates the token's cryptographic signature — proof it wasn't tampered with — but does not automatically check semantic claims like exp (expiration), iss (issuer), or aud (audience). A perfectly, validly signed token that expired yesterday will still pass n8n's built-in check.

— SECTION 03 — ADVANCED

HMAC Signature Verification

The separate mechanism Stripe, GitHub, and Shopify actually use — and why it's not the same thing as n8n's built-in JWT Auth.

Provider webhook signing works completely differently from JWT: the provider computes an HMAC hash of the raw request body using a secret only you and they share, and sends that hash in a plain header (e.g., X-Hub-Signature-256, Stripe-Signature).

hmac-verification-flow.json 
[Webhook: receives raw body + signature header]
        │
        ▼
[Crypto node: action = Hmac, type = SHA256]
  └─ computed over the RAW body
        │
        ▼
[Compare computed hash to signature header]
        │
   ┌────┴────┐
  match    no match
   │           │
   ▼           ▼
[continue]  [Stop And Error / Respond 401]
Critical Configuration

Signature verification must be computed over the exact raw bytes of the body the sender signed — not a JSON-reparsed version. Even whitespace differences change the hash. Enable the Webhook node's raw-body option whenever verifying a provider's signature.

Crypto Node Limitation

The Crypto node's Hmac action expects its secret via a dedicated Crypto credential — but there's an open, unresolved community request asking for an easy way to retrieve that same credential's secret value elsewhere in the workflow. The practical workaround: store the secret in an $env variable and reference it directly in the Crypto node's inline value field.

— SECTION 04 — CRITICAL

Timing-Safe Comparison

The one-line difference between "looks secure" and "is secure" when checking a signature.

WRONG Vulnerable
naive-compare.js 
if (computedHash === receivedSignature) {
  // proceed
}
  • • Compares character by character
  • • Returns early on first mismatch
  • • Timing leak — attacker reconstructs hash char by char
CORRECT Timing-Safe
secure-compare.js 
const crypto = require('crypto');

const computed = Buffer.from(
  $json.computed_hash, 'hex'
);
const received = Buffer.from(
  $json.signature_header
    .replace('sha256=', ''), 'hex'
);

const isValid = computed.length === received.length &&
  crypto.timingSafeEqual(computed, received);

if (!isValid) {
  throw new Error('Signature failed');
}
  • • timingSafeEqual — constant time
  • • No early return on mismatch
  • • Length check first (prevents throw leak)
Why This Matters

A naive comparison returns as soon as it finds a mismatch. A wrong guess matching the first three characters takes measurably longer to reject than one wrong from the first character. Repeated over enough requests, an attacker uses that timing difference to reconstruct the correct hash — a real, documented class of attack.

— SECTION 05 — DEFENSE IN DEPTH

Complementary Layers

IP allowlisting and payload-size limits as independent, additional security layers.

IP ALLOWLISTING

The Webhook node's IP Whitelist option restricts which network addresses can reach the endpoint at all.

webhook-config.json 
"ipWhitelist": [
  "192.30.252.0/22",
  "185.199.108.0/22"
]

Genuinely useful when a provider publishes a fixed set of sending IPs.

PAYLOAD LIMITS

N8N_PAYLOAD_SIZE_MAX caps how large a single request body can be — defaulting to 16 MB.

.env 
N8N_PAYLOAD_SIZE_MAX=16777216

Direct defense against resource-exhaustion: enormous bodies consuming memory and processing time.

— SECTION 06 — SUMMARY

Security Decision Matrix

Which authentication method for which caller relationship.

Scenario Method Why
Internal service-to-service Header Auth You control both ends, can rotate keys
Multi-tenant SaaS JWT Auth Each client has their own signed token
Stripe / GitHub / Shopify HMAC Verify Provider signs payload with shared secret
Legacy / simple caller Basic Auth Caller supports nothing else
Prototype / testing None Never in production
— SECTION 07 — QUIZ

Test Your Understanding

Three questions testing deep comprehension of webhook security architecture.

1. You configure "Retry On Fail: 3 tries" but set On Error to "Continue (using error output)." What happens?

All 3 retries execute, then failed items route to error output
Attempt 1 fails, immediately routes to error output — retries 2 & 3 never happen
The workflow stops with an error saying the settings are incompatible
n8n automatically changes On Error to "Stop Workflow" to allow retries

2. What's the difference between JWT Auth and HMAC signature verification for webhooks?

They are the same thing — JWT is just a specific type of HMAC
JWT verifies a structured token format; HMAC recomputes a hash of the raw body and compares it to a header
JWT is for internal APIs; HMAC is only for payment providers
HMAC requires RSA keys; JWT works with simple shared secrets

3. Why is === (strict equality) dangerous when comparing a webhook signature?

It throws an error if the hashes don't match, leaking information
It returns early on first mismatch, creating a timing difference attackers can measure
It doesn't handle hex-encoded strings correctly
It's slower than timingSafeEqual for long strings
